🐛 Fuzz Testing — let the machine find your bugs

Fuzzing means throwing huge numbers of automatically generated inputs at a program and watching for crashes. Pure random fuzzing finds shallow bugs fast but is blind to anything behind a specific check like if (magic == "FUZZ"), since the odds of guessing four exact characters are about 1 in 80 million. Coverage-guided fuzzers (AFL, libFuzzer, go test -fuzz) add one trick: when an input reaches new code, keep it and mutate it further. Each correct character opens a new branch, so the fuzzer works through the check one character at a time. Start the race below.

How it works

  

    

      
Born in a thunderstorm
In 1988 Barton Miller noticed that line noise over a dial-up connection was crashing Unix programs. His class then fed random input to standard Unix utilities, and roughly a quarter to a third of them crashed or hung.

      
The feedback loop
Run the input, record which branches it hit, and keep it in the corpus if it reached anything new. Then pick a corpus entry, mutate it (flip, insert or delete a byte), and repeat millions of times. Coverage turns a blind search into hill-climbing.

      
Crash = finding
Fuzzers flag crashes, hangs, and (with sanitizers like ASan) silent memory errors. Each crashing input is saved as a ready-made reproducer you can turn into a regression test.

      
At scale
Google's OSS-Fuzz runs continuously on 1,000+ open-source projects and has reported tens of thousands of bugs, many of them security holes. Go has had built-in fuzzing since 1.18: write func FuzzX(f *testing.F) and run go test -fuzz=FuzzX.

    

    
Model note: inputs are 0–10 printable ASCII characters. The guided fuzzer starts from the seed "seed" and uses replace/insert/delete mutations. Both fuzzers get the same number of executions.
